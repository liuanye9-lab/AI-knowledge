# 项目优先的学习与 Agent 协同框架

## 产品判断

普通用户不需要先完成一套 AI 课程。更合适的主线是：让用户带着现实需求进入，由系统先判断 AI 是否适合介入，再以完整示例帮助他完成一次项目；知识只在当前决策点出现，并在成功后由 Agent 沉淀为可复用方法。

原有知识内容继续保留，但从“必经主线”调整为“遇到卡点时按需打开的参考层”。

## 研究依据及产品推论

1. **先给完整示例，再逐步减少帮助。** Worked examples 对新手能降低问题求解时的认知负荷；随着熟练度提升再逐步撤掉支持，比一开始要求独立操作更合适。产品因此先展示一份可用成果和完整执行路径，而不是先讲框架。[Worked examples 研究](https://pubmed.ncbi.nlm.nih.gov/34458621/)；[支持逐步淡出研究](https://pubmed.ncbi.nlm.nih.gov/40329570/)
2. **用真实场景承载方法。** 具体例子、提取练习、间隔练习、精加工和双编码都有较稳定的学习证据。产品不把它们做成测验，而是在相似项目再次出现时，让用户认出并确认上次用过的方法。[学习科学综述](https://pubmed.ncbi.nlm.nih.gov/29399621/)；[提取练习综述](https://pubmed.ncbi.nlm.nih.gov/20951630/)
3. **解释不等于信任校准。** 解释可能同时增加用户对正确和错误结果的依赖；来源、不一致提示和明确的确认点更能帮助用户适当使用 AI。产品因此不展示长篇“AI 为什么这样想”，而展示来源、缺口、风险和需要人确认的选择。[CHI 2025 研究](https://www.microsoft.com/en-us/research/publication/fostering-appropriate-reliance-on-large-language-models-the-role-of-explanations-sources-and-inconsistencies/)
4. **人确认策略，Agent 执行步骤。** 对复杂 Agent 任务，逐步审批会制造疲劳；先展示整体计划，让人确认目标、边界和高影响动作，更符合人的决策角色。产品采用项目级确认、风险动作再次确认的双层机制。[可信 Agent 实践](https://www.anthropic.com/research/trustworthy-agents)
5. **团队表现优先于单模型准确率。** 最准确的模型不一定是最好的协作者，系统还应考虑错误代价、核验成本和人与 AI 各自擅长什么。产品的路由目标是“用足够低的成本安全完成任务”，而不是永远调用最强模型。[Human-AI team utility 研究](https://www.microsoft.com/en-us/research/publication/is-the-most-accurate-ai-the-best-teammate-optimizing-ai-for-teamwork/)

以上第 3–5 点到具体界面的映射属于基于研究的产品推论，不是论文直接验证过的最终界面结论，仍需用真实用户任务测试。

## 统一项目循环

1. **需求**：用户只描述想得到的结果，可来自主页、新标签页、当前网页或飞书消息。
2. **适用性判断**：系统判断 AI 是否适合、能节省什么、主要风险是什么。
3. **工作示例**：Agent 先形成一份完整初稿，让新手看到“完成后是什么样”。
4. **决策闸门**：人只确认目标、关键事实、取舍、权限、对外承诺和不可逆动作。
5. **Agent 执行**：Agent 负责拆解、调用工具、整理、检查、记录与协同。
6. **结果交付**：产出文档、任务、表格、消息或其他可验证成果。
7. **方法沉淀**：系统从成功项目中提炼触发条件、输入、步骤、检查项和权限边界，形成 Skill 草稿。
8. **相似场景再用**：再次遇到相似任务时先召回 Skill；用户只确认差异，不重新学习整套流程。

## 人与 Agent 的责任边界

| 人负责 | Agent 负责 | 必须再次确认 |
| --- | --- | --- |
| 目标、价值取舍、真实意图 | 搜集、整理、生成、执行、记录 | 付款、发送、删除、授权、隐私、对外承诺 |
| 判断结果是否符合现实 | 提供来源、标记不确定、进行一致性检查 | 医疗、法律、财务等高影响判断 |
| 决定是否把方法纳入个人或团队流程 | 形成 Skill 草稿与适用范围 | Skill 获得新的外部写入权限 |

## Agent 与 Agent 协同

默认不让多个 Agent 自由讨论，而采用可审计的明确分工：

1. **协调 Agent**：理解需求、拆分工作、选择已有 Skill，并决定是否需要其他 Agent。
2. **执行 Agent**：调用具体工具完成步骤，不改变目标和权限。
3. **核验 Agent**：独立检查来源、遗漏、矛盾和高风险动作；不负责美化原结果。
4. **沉淀 Agent**：只在结果已经被用户接受且流程重复成功后，整理 Skill 草稿。

低风险线性任务优先使用单 Agent，只有任务可以独立拆分、需要不同工具或需要独立核验时才增加 Agent，避免为了“多 Agent”而增加成本与错误面。

## Skill 最小结构

```json
{
  "name": "会议纪要转任务",
  "trigger": "会议结束且存在行动项",
  "inputs": ["会议记录", "成员名单", "时间约束"],
  "steps": ["提取结论", "识别行动项", "补齐责任字段", "等待确认", "创建任务"],
  "checks": ["每项有负责人", "每项有截止时间", "承诺得到确认"],
  "output": "可追踪的飞书任务",
  "permissions": { "read": ["会议记录"], "write": ["任务草稿"], "approval": ["发送通知"] },
  "evidence": { "successful_runs": 3, "last_verified": "2026-07-23" }
}
```

只有重复、成功、可验证且权限安全的流程才成为 Skill；一次性的偏好和未经核验的模型输出不自动沉淀。

## 界面信息优先级

第一屏只显示：

1. 这件事是否值得用 AI；
2. 最终能得到什么成果；
3. Agent 会做什么；
4. 用户只需确认什么；
5. 一个开始按钮。

第二层按需显示执行步骤、工具组合、来源和风险。第三层才链接到完整基础知识、原理与技术框架。
