# AI 伴学产品完整度自查

日期：2026-07-22

## 结论

当前版本已经超过“静态概念 Demo”：入口页、新标签页、侧边栏、页面读取、三种结果模式、本机 Codex Agent Bridge、飞书 CLI 深链和云端模型网关都已有代码与局部验证。

但它仍属于“可演示的工程原型 / pre-alpha”，还不是普通用户可从 Chrome Web Store 安装后稳定使用的完整产品。核心原因不是视觉，而是主流程里仍有三段未产品化：云端 AI 尚未启用；本机 Agent 需要手工安装且仅有 Windows 方案；隐私、身份、监控、发布和支持体系尚未建立。

## P0：上架前必须解决

### 1. 定义可审核的单一目的

建议将商店版的单一目的写成：

> 用户主动打开侧边栏时，把当前网页或选中文字转成一个可执行结果，并解释本次使用的 AI 方法与边界。

新标签页只能作为这一个目的的轻量入口，不应成为独立的通用搜索产品；飞书与 Codex 应作为结果交接和高级连接能力。否则“新标签页 + 搜索 + 网页理解 + 写作 + 飞书 CLI + 本机 Agent”容易被审核视为功能捆绑。

### 2. 把“示例结果”变成可运营的 AI 服务

- 当前线上模型网关未配置 API Key，所有公网用户都会进入本地模板。
- 需要生产模型路由、超时与重试、使用额度、成本上限、供应商故障切换和清晰的离线状态。
- 固定模板必须明确标注为“离线方法”，不能让用户误以为模型已经处理了网页。

### 3. 重做后端安全边界

- 当前接口允许无 `Origin` 请求，也允许任意 `chrome-extension://` 来源；CORS 不是身份认证。
- 内存 `Map` 限流不适合无状态 Serverless，多实例和冷启动会绕过限制。
- 需要最少具备：用户或安装实例身份、短期访问令牌、持久化限流、配额、审计日志、异常监控、供应商调用追踪、密钥轮换和滥用封禁。
- 企业内容需要可选择“仅本机 Codex”“云端模型”或“不要发送”，并在第一次发送网页内容前取得明确同意。

### 4. 将 Native Agent 做成独立桌面伴侣

Chrome Web Store 只分发扩展，不能替用户安装 Native Messaging Host。因此必须另做：

- Windows 签名 MSI/EXE；macOS 签名并公证的 PKG/DMG；
- 固定商店扩展 ID，并把它精确写入 Native Host 的 `allowed_origins`；
- 自动检测 Codex CLI / 飞书 CLI、登录状态和版本；
- 一键修复、自动更新、卸载、日志导出；
- 扩展在没有桌面伴侣时仍能完成云端核心流程。

当前 PowerShell 脚本会在用户机器上现场编译 C#，适合开发，不适合大众分发。

### 5. 建立隐私与同意流程

产品处理“当前网页内容、网址、用户选区”，这些都属于需要披露的用户数据。上架前需要：

- 独立隐私政策页面与可联系的支持邮箱；
- 首次使用时的显著披露：读取什么、何时读取、发给谁、保存多久、如何删除；
- 云端处理前的明确同意；本机处理与云端处理分开说明；
- Chrome Web Store Privacy practices 与产品实际行为、隐私政策完全一致；
- 第三方模型供应商的数据保留、训练使用、地区、子处理方和删除机制完成书面核验。

## P1：封闭测试前解决

- **真实浏览器端到端测试**：现有 24 项测试通过，但主要是结构与静态断言，不能覆盖权限、服务工作线程、Native Messaging、受限页面与更新迁移。
- **输入提取质量**：当前只取选区或页面前 8,000 字符；长文、表格、代码、PDF、动态页面会丢上下文。需要可见范围优先、结构化提取、来源引用和用户预览。
- **响应体验**：Codex 可能需要十几秒到近一分钟；需要阶段进度、取消、超时、重试、后台完成通知和防重复提交。
- **无障碍**：Agent 在线状态目前主要靠彩色圆点表达；应增加“已连接/未连接”文本与可读状态。加载状态需要 `aria-busy`，模式切换需要明确选中语义。
- **安装说明真实性**：当前页面声称三步自动完成，但本机 Agent 并不会随扩展自动安装；应区分“基础版已可用”和“高级本机能力待连接”。
- **版本与文档一致性**：README 声明的权限列表漏掉了 `nativeMessaging` 与 `topSites`；商店权限说明必须与 Manifest 一致。
- **商店包清理**：当前 ZIP 同时包含根目录与子目录的重复页面、脚本和图标；应建立确定性构建，只输出实际运行文件、LICENSE、必要声明与 source map 策略。
- **恢复和支持**：增加设置页、权限状态、连接诊断、隐私开关、反馈入口、版本信息、更新说明和数据清除。

## 推荐的完整架构

```text
Chrome 扩展
  ├─ 新标签页：轻入口，可关闭
  ├─ 侧边栏：当前页 → 直接结果 → 方法 → 风险
  └─ 设置/诊断：权限、隐私、模型、桌面伴侣
          │
          ├─ 云端控制面
          │   ├─ 身份与安装实例
          │   ├─ 模型路由、配额、限流、审计
          │   ├─ 用户设置/记忆/删除
          │   └─ 监控、告警、支持
          │
          └─ 可选桌面伴侣
              ├─ Codex CLI 只读 Agent
              ├─ 飞书 CLI / 官方连接器
              ├─ Native Messaging
              └─ 签名、自动更新、卸载
```

推荐发布顺序：商店基础版先保证“无需桌面伴侣也能完成当前页处理”；桌面伴侣作为高级、本地优先能力独立安装。这样既保留 Codex/飞书深度，又不让核心价值依赖复杂环境。

## Chrome Web Store 完整流程

### 阶段 A：产品与合规冻结

1. 冻结单一目的、数据流图、权限清单和支持平台。
2. 删除非必要权限；每个权限准备一段用户价值与审核解释。
3. 完成隐私政策、显著披露、同意、数据删除和供应商审查。
4. 完成 Manifest V3 检查，所有可执行逻辑随扩展打包，不能远程加载代码。

### 阶段 B：工程产品化

1. 建立生产/预发布环境、身份、持久化限流、配额、日志、告警和密钥轮换。
2. 为 Windows/macOS 构建签名桌面伴侣；把商店稳定 ID 写入 Native Host 白名单。
3. 建立单元、集成与真实 Chrome E2E：安装、升级、权限拒绝、离线、模型超时、Native Host 缺失、Codex 未登录、飞书未授权、卸载。
4. 用封闭用户完成可用性、隐私理解和故障恢复测试。

### 阶段 C：准备商店材料

1. 注册 Chrome Web Store 开发者账号、同意协议、支付一次性注册费，并启用 Google 账号两步验证。
2. 生成干净 ZIP；检查 `name`、`version`、description、图标、权限和最低 Chrome 版本。
3. 准备清晰商店文案、支持链接、隐私政策、至少 1 张实际功能截图；截图使用 1280×800 或 640×400，建议准备 3–5 张。
4. 准备审核测试说明；如果高级功能需要桌面伴侣或登录，提供可复现步骤与测试账号/环境。

### 阶段 D：上传、审核、发布

1. Developer Dashboard → Add new item → 上传 ZIP。
2. 填写 Store listing、Privacy、Distribution、Test instructions。
3. 先设为受限/测试分发，提交审核并选择延迟发布。
4. 根据拒绝原因修复后提升版本号、重新打包和提交；不要只改商店文案掩盖真实行为。
5. 审核通过后先小范围发布，观察崩溃、延迟、模型成本、卸载和用户反馈，再逐步扩大。

### 阶段 E：上线后运营

- 每次代码或资源更新都提升 Manifest 版本、重新上传并再次审核。
- 持续跟踪政策变化、权限变化、供应商条款、支持工单、评分与异常。
- 建立回滚、功能开关、状态页、事故响应、数据删除 SLA 和版本兼容策略。

## 进入开发前的验收门槛

只有以下条件同时成立，才应称为“可提交商店的 Beta”：

- 新用户从商店安装到第一次有效结果不超过 2 分钟，且无需阅读技术说明；
- 没有桌面伴侣时，核心侧栏流程仍可用；
- 用户在发送网页内容前明确知道内容会去哪里；
- 模型、网络、权限、Native Host、Codex 和飞书任一失败都有可理解的恢复路径；
- Chrome 真实 E2E、Windows/macOS 安装升级、隐私和滥用测试通过；
- 后端具备身份、持久化限流、配额、监控和删除能力；
- 商店材料、权限解释、隐私政策和实际行为一致。
