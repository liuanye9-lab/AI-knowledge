# 企业实操专栏升级设计

日期：2026-07-20  
目标页面：`practice.html`  
目标读者：想用 AI 提效、但不熟悉技术名词、产品边界和开发流程的个人与企业新手

## 1. 目标

把现有企业专栏升级为一条可操作的学习路线，让新手读完后能够回答三件事：

1. 飞书每类产品解决什么问题，什么时候该用，什么时候不该用。
2. AI 如何通过飞书 CLI 把文档、消息、会议、任务和业务数据串成闭环。
3. 如何在 AI Agent 帮助下，把一个产品从想法推进到本地验收、版本管理、上线和持续运营。

页面保持现有静态 HTML/CSS/JS 架构，不引入框架和构建流程。修改范围聚焦于 `practice.html`、全站导航、必要的样式、少量交互脚本和配套插图。

## 2. 第一性原理写法

每个产品、概念和步骤优先回答下面五个问题：

1. **为什么需要它**：它替人解决哪一种重复劳动或信息断点。
2. **输入是什么**：文档、消息、表格记录、会议录音还是人的一句话。
3. **中间发生什么**：AI 负责理解或生成，飞书产品负责存储、协作、权限或触发。
4. **输出是什么**：一份文档、一条任务、一条业务记录、一次通知或一个可访问的应用。
5. **边界在哪里**：需要什么权限、什么必须人工确认、何时不适合继续使用这一方案。

正文使用大白话，首次出现的专业名词立即给出生活化解释。例如：

> API 就像服务窗口。你不需要走进档案室，只要按规定提交一张表，窗口就会把结果交给你。

不使用“赋能、抓手、全链路、无缝闭环”等空泛表达。每段只讲一个判断，结论先行。

## 3. 信息架构

页面沿用现有 `station` 章节系统，调整为八个连续站点。

### 站点一：企业 AI 提效地图

用一句总原则开场：

> **AI 负责理解和生成，飞书负责让信息有地方存、有人协作、有权限约束、有流程继续往下走。**

展示四层路径：

- 个人：提问、写作、总结。
- 团队：文档、会议、任务和消息协作。
- 业务：多维表格、审批、工作流和仪表盘。
- 系统：Aily、妙搭、开放平台和飞书 CLI。

### 站点二：飞书产品能力地图

不按产品宣传页罗列，而按工作对象分组。

| 能力层 | 代表产品 | 适合做什么 | 不适合做什么 |
|---|---|---|---|
| 内容资产 | 文档、知识库、云盘、表格、幻灯片、白板 | 共创、沉淀、搜索、引用和版本协作 | 代替需要强事务一致性的业务数据库 |
| 结构化业务 | 多维表格、表单、仪表盘、自动化、工作流 | 轻量 CRM、项目台账、内容排期、信息收集和统计 | 默认当作无限容量、高并发的通用后端 |
| 协作执行 | 消息、日历、任务、邮件、会议、妙记 | 把结论变成负责人、截止时间和下一次行动 | 未经确认代表用户对外承诺或群发 |
| 组织管理 | 通讯录、审批、考勤、OKR | 在授权范围内查询或更新组织流程数据 | 绕过管理员、审批人或数据权限 |
| AI 应用 | 飞书 AI、Aily | 企业知识问答、会议总结、Agent、固定工作流和混合调度 | 自动保证答案正确，或越过原始知识权限 |
| 应用交付 | 妙搭、开放平台、飞书 CLI | 搭应用、接系统、批量处理和自动执行 | 代替完整的产品设计、安全评审和人工验收 |

具体额度、行数和高级权限随飞书版本变化。页面只解释差异方向，并链接当前官方权益页，不把易过期数字写成永久结论。

### 站点三：飞书 AI、Aily 与 CLI 的区别

用“脑、流水线、手”的比喻：

- **飞书 AI 是现成的脑力助手**：普通成员直接总结、问答和生成。
- **Aily 是 AI 应用装配台**：把知识、Agent 技能、固定 Workflow 和触发方式组合成企业应用。
- **飞书 CLI 是 AI 的操作手**：在授权范围内读写文档、表格、消息、日历、任务、会议记录和应用资源。

明确说明：三者可以组合，但不是同一个产品，也不会自动共享所有权限。

### 站点四：六个飞书 CLI 价值闭环

每个案例使用相同卡片结构：“原来怎么做 → CLI 串什么 → 最终价值 → 人工确认点”。

1. **每日工作简报**  
   日历 + 我的任务 + 重要邮件 + 待处理消息 → 一页今日重点。

2. **会议闭环**  
   查日程 → 读取妙记 → 提炼结论 → 创建任务 → 通知负责人。  
   发消息、建任务和邀请他人属于写入动作，执行前确认。

3. **企业知识运营**  
   搜索文档和知识库 → 找出重复问题与内容缺口 → 更新 FAQ → 记录变更。  
   不把无来源的模型回答直接写成公司制度。

4. **销售跟进**  
   会议记录或邮件 → 多维表格客户记录 → 跟进任务 → 下次日程。  
   报价、承诺和客户敏感信息必须由人审核。

5. **经营周报**  
   读取多维表格 → 汇总指标 → 生成文档 → 发给指定群。  
   AI 解释趋势，原始数字仍以数据表为准。

6. **AI 应用交付**  
   妙搭创建或接管应用 → 本地或云端迭代 → 发布 → 查看日志、错误率、延迟和访问量。  
   CLI 能管理发布与观测，但应用内 RBAC 和部分自动化仍需网页端配置。

页面给出可复制的自然语言指令，不直接展示含真实 ID、密钥或令牌的命令。进阶用户可展开查看命令组成。

### 站点五：AI Coding 从想法到本地成品

将原始 20 步压缩为五个阶段，避免连续 20 个同权重点造成注意力疲劳。

#### 阶段 A：选工具，也选名字

- 先试用再购买 Coding Plan，确认它支持你要使用的 Agent。
- 优先选择官方明确支持的组合；不宣称“自家 Agent 一定最好”。
- 产品名要检查公众号、小程序、应用商店、域名和基础商标冲突。
- 名字确定后尽早注册合适域名，但不鼓励冲动购买高价域名。

#### 阶段 B：在本地做出第一版

- 新建同名项目文件夹。
- 在该文件夹启动 Agent。
- 先用 Plan 模式把目标、用户和第一版核心功能说清楚。
- 让 Agent 小步实现；每完成一块就本地预览和验收。

#### 阶段 C：给项目装上安全绳

- 初始化 Git，推送到 GitHub 私有仓库。
- 建立项目说明、设计决策和 AI 规则文件。
- 使用测试、分支、PR 和 CI 保护稳定版本。
- 私有仓库分支保护的套餐要求链接 GitHub 官方说明，不把月费写死。
- `neat-freak` 作为可选第三方 Skill 推荐：注明 MIT 许可、社区维护、使用前先审阅 `SKILL.md`，并说明它负责项目知识收尾，不代替测试和代码评审。

#### 阶段 D：选择合适的上线方式

先问“产品需要什么”，再决定是否买服务器：

- 纯静态页面：优先静态托管、对象存储或 Serverless。
- 轻量应用：可选妙搭、云开发或托管平台。
- 需要长期运行的服务、数据库或自定义运维：再考虑云服务器。

使用中国大陆服务器对外提供网站服务时，依法办理 ICP 备案；官方办理时限以通信管理部门和接入商说明为准。使用境外基础设施不等于可以忽略目标市场的隐私、内容、支付和数据合规要求。

#### 阶段 E：上线后进入迭代

标准循环：

> 新分支 → 说需求 → Agent 实现 → 本地验收 → 测试 → 整理文档 → PR → CI → 合并 → 发布 → 观察指标

最后强调两条原则：

- **可以不会写代码，但必须说得清功能和数据怎么流动。**
- **AI 是执行者，产品判断、风险承担和最终验收仍由人负责。**

### 站点六：日常岗位提效

保留现有岗位表格，但减少泛化描述，为每种岗位补一个“今天就能做”的入口，并链接到前面的飞书 CLI 闭环。

### 站点七：治理、成本与运维

合并现有治理内容与上线后风险：

- 数据分级和最小权限。
- 人在回路与外部写入确认。
- 密钥只放服务端或安全环境变量。
- 备份、日志、告警和恢复演练。
- 缓存、限流、防爬、防 DDoS 和账单告警。
- AI 额度、自动化次数、服务器带宽和第三方 API 的成本上限。

运维内容讲“什么时候需要开始关注”，不要求新手一开始掌握全部术语。

### 站点八：官方资料与更新时间

资源分为三类：

- 官方产品能力与权益。
- 官方开发文档与开放平台。
- 经核验的社区工具和教程。

每个会快速变化的产品信息标注“核对日期：2026-07-20”。

## 4. 视觉与注意力设计

### 水彩视觉

沿用现有低饱和鼠尾草绿、灰蓝、陶土和淡紫配色，以及纸张、虚线和不规则圆角。插图使用柔和水彩、纸张纹理、自然留白和轻微手绘线条，不使用赛博霓虹、玻璃拟态或高对比科技蓝。

新增三张 16:9 插图：

1. **飞书协作花园**：文档、消息、会议、任务和表格像不同工作台，由柔和路径连接。
2. **AI + 飞书 CLI 闭环**：人提出目标，AI 理解，CLI 操作飞书，结果回到人验收。
3. **从想法到上线的航线**：名字与域名、本地项目、Git 安全绳、上线和持续运营五个停靠点。

插图不烧录关键文字。精确信息由 HTML 标题、标签和图注呈现，保证移动端和无障碍可读性。现有企业 AI 主视觉继续复用，避免整页风格跳变。

### 注意力分层

每个站点只设置一个一级注意力锚点：

- 第一眼：大标题和一句加粗结论。
- 第二眼：3–6 张卡片、阶段或流程节点。
- 第三眼：可展开的边界、命令和官方来源。

排版规则：

- 关键判断使用 `<strong>`，每段最多突出一处，不整段加粗。
- 一个正文段落尽量不超过四行。
- 每张卡只表达一个动作或判断。
- 同层并列不超过六项；超过时分组或折叠。
- 危险事项使用柔和陶土色警示框，行动建议使用鼠尾草绿色。
- 专业细节进入 `<details>`，默认不抢占新手注意力。
- 页面内吸顶目录显示当前章节，移动端保持横向可滚动。

## 5. 交互设计

- 保留现有锚点导航和沙盒逻辑。
- 新增“我想解决什么”选择器：知识、会议、数据、协作、做应用。选择后高亮对应飞书能力和 CLI 案例。
- AI Coding 五阶段支持逐段展开，但核心步骤在无 JavaScript 时仍可完整阅读。
- 命令示例提供复制按钮；复制内容只包含占位符，不包含真实账号、Token、App ID 或群 ID。
- 外链统一在新标签页打开，并设置 `rel="noopener noreferrer"`。

## 6. 安全与事实边界

- 飞书能力以当前企业版本、管理员开通范围、用户授权和 OpenAPI Scope 为准。
- Bot 身份不能代表用户访问私人资源；用户身份也只能访问该用户本来有权访问的内容。
- 任何发消息、发邮件、改业务数据、邀请成员、发布应用等外部写入，都在示例中标注确认点。
- Coding Plan 与 Agent 的兼容组合以厂商官方支持列表为准，不把 API Key 能填进去等同于套餐允许使用。
- 不建议默认开启自动批准或跳过权限确认。
- 不把“让 Agent 操作浏览器”描述成万能方案；账号、付款、备案、权限和不可逆操作需要人核对。
- ICP 表述以“在中国大陆提供互联网信息服务需要依法备案”为准，不使用“所有未备案域名都会被运营商拦截”的绝对描述。

## 7. 验证标准

实施完成后至少验证：

1. HTML 无明显结构错误，所有章节锚点可访问。
2. 桌面端与移动端均不存在横向页面溢出。
3. 吸顶目录、高亮、折叠和选择器可用；关闭 JavaScript 后核心内容仍可读。
4. 三张新插图加载正常，具有准确 `alt` 文本、宽高属性和合理文件体积。
5. 外链无空地址，官方来源与第三方来源有明确区分。
6. 页面中不包含密钥、真实账号 ID 或个人授权信息。
7. 对重点句、警示框和正文进行对比度检查。
8. 抽查新手阅读路径：三分钟内能找到“飞书能做什么”“CLI 有什么价值”“怎样把产品做上线”三个答案。
